# Vesta Trade AI Consultant

AI-консультант интернет-магазина инженерной сантехники «Веста Трейдинг». Бот
работает как продавец-консультант: понимает живую речь клиента, доводит запрос
до состояния «можно подбирать», ищет товар в XML-фиде магазина и показывает
карточки с ценой, наличием и прямой ссылкой — но только после того, как
собраны инженерно обязательные параметры и ответ прошёл проверку на выдумки.

Главный принцип архитектуры: **LLM объясняет и понимает, но не решает и не
выдумывает факты**. Что показать клиенту, хватает ли данных для подбора и какие
цифры назвать — решает детерминированный код по данным фида. LLM подключается
там, где регулярки объективно слабы (свободная речь, короткий ответ на вопрос,
объяснение выбора), и её вывод всегда перепроверяется.

## Быстрый старт

```bash
cd vestatrade_bot
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Запуск:

```bash
uvicorn app.main:app --reload
```

Открыть чат: `http://127.0.0.1:8000`

### Локальный запуск V2 Preview

Для разработки и проверки V2 на другом компьютере не нужно вручную включать
canary или менять публичный маршрут. После настройки `.env` запустите:

```bash
./scripts/start_v2_preview.sh
```

Откройте `http://127.0.0.1:8010/widget-v2-preview`. Скрипт поднимает сервер
только на loopback, включает защищённый `v2_preview` для этой страницы и
оставляет обычный `/chat` в Legacy-режиме, а `canary=0`. Ключ OpenRouter в Git
не хранится: добавьте `OPENROUTER_API_KEY` и `LLM_PROVIDER=openrouter` только
в свой локальный `.env`; либо используйте настроенный локальный Ollama.
Для автоматического перезапуска при изменении кода используйте
`V2_PREVIEW_RELOAD=1 ./scripts/start_v2_preview.sh`.

### Обычный виджет через V2-first

V2-first использует тот же публичный путь, что и прежний бот:

```text
виджет сайта → /chat → V2 → Legacy fallback при отклонении V2-gate
```

Для включения на сервере требуются одновременно:

```dotenv
DIALOGUE_V2_ROUTING_ENABLED=true
DIALOGUE_V2_LIVE_DELIVERY_ENABLED=true
DIALOGUE_V2_PUBLIC_PRIMARY_ENABLED=true
DIALOGUE_V2_INTERNAL_CANARY_ENABLED=false
DIALOGUE_V2_INTERNAL_CANARY_PERCENT=0
DIALOGUE_V2_FORCE_LEGACY=false
COMMERCE_EXTERNAL_EXECUTION_ENABLED=false
```

V2 остаётся первым владельцем только после успешных semantic, contract,
source и outcome-gates. Если хотя бы один из них не проходит, этот конкретный
ход отвечает Legacy. Для немедленного отката достаточно выставить
`DIALOGUE_V2_FORCE_LEGACY=true` и перезапустить сервис.

При старте сервер загружает каталог: локальный XML (`FEED_FILE_PATH`), иначе
удалённый фид (`FEED_URL`), иначе последний кэш `app/data/products_cache.json`.
Пока каталог не загружен, `/ready` отвечает `503`. Пустой результат парсинга
никогда не затирает рабочий кэш.

Проверить, какая LLM реально подключена и отвечает ли она:

```bash
.venv/bin/python scripts/check_llm.py
```

Если LLM не настроена, недоступна или исчерпан дневной бюджет — бот **не
падает**: LLM-вызовы отключаются, работает детерминированный fallback.

## Как обрабатывается одно сообщение

`POST /chat` → `ChatOrchestrator.handle_chat` (`app/agents/orchestrator.py`).

Обработка одной реплики **транзакционна**: ход одной сессии сериализуется
(локальный `RLock` + распределённая блокировка Redis), состояние снимается до
хода и откатывается целиком при исключении. Разные пользователи идут
параллельно. Все LLM-агенты одной реплики делят **один дедлайн**
(`LLM_REQUEST_TIMEOUT_SECONDS`, по умолчанию 180 с).

Порядок этапов внутри `_handle_chat`:

**1. Детерминированные перехваты — до любой LLM.**
Безопасность (газ, электрика, аварийная течь, эксплуатация водонагревателя),
границы бота («ты человек?», «приедете смонтировать?»), контакты и согласие на
передачу менеджеру, возврат к ранее обсуждённой ветке («вернёмся к тёплому
полу»), подтверждение уже собранных требований. Эти пути не зависят от
вероятностного роутера и не отправляют PII во внешнюю модель.

**2. `IntentRouterAgent.route`** — тип запроса, категория, слоты, бренд, SKU,
флаги («подешевле», «в наличии»), смена темы. Сначала правила; LLM вызывается
только при `confidence < 0.55`, её ответ проходит sanity-check и ограничен
закрытым списком `VALID_INTENTS`. Результат кэшируется по ключу, включающему
контекст сессии.

Типы интентов: `exact_sku`, `brand_category`, `broad_category`, `cheap_request`,
`stock_request`, `attribute_request`, `complectation`, `small_talk`,
`out_of_scope`, `unknown`.

Категории: `pipes`, `pumps`, `boilers`, `water_heaters`,
`hydraulic_accumulators`, `filters`, `controls`, `valves`, `sewer`,
`radiator_fittings`, `radiators`, `fittings`, `other`.

**3. `PendingAnswerResolver`** — привязка короткого ответа («25», «полдюйма»)
к тому слоту, который бот реально спрашивал. Запускается только если правила
ничего не вычитали. Модель может выбрать **только** ключ из переданного списка
и **только** значение, дословно присутствующее в сообщении; результат
перепроверяется по типизированной спецификации слота (диапазон, единица,
допустимые значения).

**4. `EngineeringInterpreterAgent`** — понимание бытовой речи до поиска: связать
реплику с предыдущим вопросом, перевести «три кольца колодца» в метры, «литры в
минуту» в расход. Возвращает JSON только с **исходными** фактами клиента с
цитатой-подтверждением на каждый слот. Расчётные величины (напор, глубина,
длина трубы) модель возвращать не имеет права — их считает
`engineering_calculations` детерминированно.

**5. Заземление на каталог** — SKU и бренд подтверждаются по фиду. Если точный
артикул относится к другой категории, чем считал роутер, авторитетен фид: это
трактуется как смена ветки.

**6. Специализированные детерминированные ответы** — вопросы о показанной
карточке (комплектация, назначение, присоединение, электрика), сравнение
позиций, «дай ссылку», пагинация «покажи ещё», проектная корзина
(`project_specification.py`), уточнение противоречий.

**7. `EngineeringRequirementsAgent.assess` → `SlotFillingAgent`** — инженерный
гейт. Проверяет по `selection_contracts`, собраны ли обязательные факты
(участок и режим трубопровода, температура и давление; для насоса — назначение,
расход, напор или маркировка заменяемого). Не хватает — задаётся **один**
следующий вопрос, а в сессию пишется типизированное `PendingQuestionState`
(ожидаемые слоты, а не текст вопроса), чтобы перефразировка вопроса не ломала
привязку ответа.

**8. `ConsultantAgent`** — консультативные и проектные разговоры («строю дом
240 м²», «что ещё нужно?»). LLM рассуждает по предметной рамке и опирается на
реальные товары из фида (`FeedSearchAgent.retrieve_for_consult`). Если LLM
недоступна — возвращает `None`, и пайплайн продолжается детерминированно.

**9. Подбор товара:**

```
_build_query → FeedSearchAgent.search  (гибридный поиск + жёсткие фильтры)
             → RankingAgent.rank       (SKU, цена, наличие, бренд, мощность)
             → ProductCardAgent.build_cards
             → GuardrailsAgent.validate_cards
             → ResponseComposerAgent.compose_*
```

Если точного совпадения нет — `search_alternatives` / `search_nearest_variants`
с честной пометкой, чем аналог отличается. Если бренд не задан, при прочих
равных первыми идут `VALTEC`; явно запрошенный бренд всегда приоритетнее.

**10. `HandoffAgent`** — если guardrails не пропустили выдачу или клиент просит
менеджера: сводка запроса, запрос контакта, явное согласие, идемпотентная
запись заявки с ticket id (`app/data/handoff_requests.jsonl`).
Состояния: `none` → `awaiting_contact` / `awaiting_consent` →
`locally_recorded` / `failed` / `opted_out`.

**11. `_response`** — финальный слой: доп. фильтр по наличию, предупреждение
если у всех позиций нулевой остаток, очистка Markdown (виджет рендерит
`textContent`), обновление памяти о показанных товарах и сборка `debug`.

## Карта модулей

### `app/agents/` — диалог и подбор

| Файл | Ответственность |
|---|---|
| `orchestrator.py` | Оркестрация всего хода: перехваты, порядок агентов, память о показанных товарах, сборка ответа. Самый большой модуль проекта |
| `intent_router.py` | Тип запроса, категория, слоты, бренд/SKU, смена темы. Правила + LLM-fallback |
| `slot_filling.py` | Последовательное уточнение параметров подбора по категориям |
| `selection_contracts.py` | Декларативные контракты: какие канонические факты обязательны до подбора |
| `engineering_requirements.py` | Инженерный гейт + структурная память по подсистемам (трубы, насосы, котлы…), переживающая смену категории |
| `engineering_interpreter.py` | LLM-слой понимания бытовой речи → сырые факты клиента (JSON + цитаты) |
| `engineering_calculations.py` | Детерминированные расчёты производных величин (напор, глубина, потери по Дарси–Вейсбаху) |
| `engineering_notation.py` | Инженерные обозначения и сокращения по категориям (ГВС, DN, тип 22, PN) |
| `numeric_semantics.py` | Числа с привязкой к размерности: 45 — это градусы, бары, миллиметры или цена |
| `slot_answer_resolver.py` | Привязка свободного ответа к слоту + типизированная валидация значений |
| `turn_classifier.py` | Что это за ход: ответ на вопрос, просьба объяснить, запрос определения |
| `feed_search.py` | Гибридный поиск по фиду, жёсткие фильтры совместимости, аналоги, поиск по названию модели |
| `ranking.py` | Сортировка: релевантность, цена, наличие, бренд, мощность котла |
| `product_card.py` | Карточка строго из полей фида; выбор характеристик под запрос |
| `product_identity.py` | Что это за товар на самом деле (кран/фитинг/фильтр) — против ложных совпадений по названию |
| `product_constraints.py` | Резьба (ВР/НР, пары FF/FM/MM) и дюймовые размеры |
| `trade_vocabulary.py` | Монтажный сленг → семейство каталога: «американка», «сгон», «футорка», «евроконус» |
| `project_specification.py` | Состав типового проекта таблицей: узел, зачем, норма расхода, условие включения |
| `sku_suggestions.py` | Опечатка в артикуле: уникальное совпадение или явный список кандидатов (fail-closed) |
| `consultant.py` | Свободная консультация LLM в рамке предметной области, с опорой на фид |
| `response_composer.py` | Текст ответа: подбор, уточнение, отказ, сравнение, small talk, объяснение терминов |
| `guardrails.py` | Запрет выдуманных ссылок, цен, остатков, характеристик и комплектации |

| `utils.py` | Нормализация текста и артикулов, разбор «просят / отвергают», слияние слотов |

## Состояние диалога

`SessionState` (`app/models.py`) — намеренно типизированное, а не «мешок слотов».
Ключевые части:

| Поле | Зачем |
|---|---|
| `slots` | Параметры активного подбора; сбрасываются при явной смене темы |
| `project_context` | Долговременная память по подсистемам — переживает смену темы, чтобы «вернёмся к трубам» не начиналось с нуля |
| `pending_question_state` | Типизированный ожидающий вопрос: `expected_slots`, а не текст. Перефразировка вопроса не ломает привязку ответа |
| `product_branches` | Показанные подборки по веткам-категориям, с сохранением порядка показа и первой выдачи |
| `last_products` | Активная витрина последнего ответа (презентационный слой) |
| `product_focus` | Устойчивая идентичность товара, даже если карточка скрыта фильтром «в наличии» |
| `product_relation` | Связь «исходный товар → показанные аналоги» |
| `shown_product_skus` | Что уже показано — чтобы «покажи ещё» не повторяло первую страницу |
| `last_search_outcome` | Типизированный пустой результат: «точного нет» переживает один уточняющий ход |
| `handoff_*` | Состояние передачи менеджеру |

Хранилище выбирается автоматически: без `SESSION_STORE_URL` — in-memory
(нормально для одного worker в разработке), с ним — Redis с хешированными
идентификаторами сессий, TTL и распределённой блокировкой хода.

## Границы LLM и guardrails

**Где LLM разрешена:**

| Агент | Что делает | Чем ограничена |
|---|---|---|
| `IntentRouterAgent` | Классификация при низкой уверенности правил | Закрытый список интентов и категорий, sanity-check против правил |
| `EngineeringInterpreterAgent` | Понимание бытовой речи | Только сырые факты, дословная цитата на каждый слот, запрет расчётов и переноса старых фактов |
| `PendingAnswerResolver` | Привязка короткого ответа к слоту | Ключ только из списка кандидатов, значение только из текста сообщения, валидация по типизированной спецификации |
| `TurnClassifierAgent` | Что это за ход | Один `kind` из закрытого списка, никаких фактов о товаре |
| `ConsultantAgent` | Консультация и проектные разговоры | Опора на выдержку из фида; ответ проверяется на выдуманные цены/остатки/артикулы |
| `ResponseComposerAgent` | Формулировка ответа | Черновик строит код; LLM только переписывает, и любое расхождение по фактам откатывает на черновик |

**Что LLM не может ни в каком режиме:**
цены, остатки, ссылки, артикулы, характеристики, подтверждение комплектации,
решение «данных достаточно», выбор товаров, любые арифметические выводы.

**Проверки (`guardrails.py`):**

- `validate_cards` — каждая карточка сверяется с исходным `Product`: URL, цена,
  остаток, соответствие категории и всем заявленным ограничениям запроса.
- `validate_response_text` — сравнение финального текста с черновиком: не
  потеряны ли факты товара, не появились ли выдуманные характеристики; **любая
  ссылка обязана совпадать посимвольно**.
- `validate_complectation_answer` — «да» про встроенный насос/бак только если
  это написано в фиде или паспорте.
- `validate_context_answer` — цены, «шт.» и артикулы должны присутствовать в
  переданном контексте.

Провал проверки → откат на безопасный черновик или передача менеджеру, а в
`debug` пишется причина отклонения.

### Привязка паспортов к товарам

Три механизма (`docs_loader.py`), поддерживаются `.pdf`, `.txt`, `.md`:

1. **Карта** `data/product_docs_map.json` — для серийных паспортов:
   ```json
   {
     "exact-model.pdf": {"skus": ["EXACT.ARTICLE"]},
     "VT.033-034-0425.pdf": {"sku_prefixes": ["VT.033", "VT.034"]},
     "газовые котлы ARDERIA.pdf": {"brand": "Arderia", "name_contains_any": ["газовый"]}
   }
   ```
   Поле `skus` выполняет точное сравнение и предпочтительно для паспортов
   конкретных моделей; `sku_prefixes` оставлено для документов серий.
   Для PDF, где обычное извлечение теряет таблицы, правило может дополнительно
   задать `"pdf_text_mode": "layout"`.
   Документ с `"enabled": false` не прикрепляется к товарам и не попадает в
   паспортный embedding-индекс; это карантин для неподтверждённых моделей.
2. **Имя файла = артикул**: `VT.1500.0.0.pdf`, `68-2-8.pdf` (слэши → дефисы).
3. **Серия в имени**: `VT.226-227-228-1248в.pdf` раскрывается по общему префиксу.

Документы подхватываются при старте и при авторизованном `POST /reload-feed`;
их количество видно в `/health` (`product_docs_loaded`). Текст паспорта
**не подмешивается** в категорийный поиск — иначе упоминание насоса в паспорте
котла превращало бы котёл в насос.

## HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Жив ли процесс + диагностика: сколько товаров, откуда, провайдер и модель LLM, таймауты |
| `GET` | `/ready` | Readiness probe: `503`, пока каталог не загружен |
| `POST` | `/chat` | Основной эндпоинт диалога |
| `POST` | `/reload-feed` | Перезагрузка каталога (нужен `X-Admin-Token`) |
| `GET` | `/` | Демо-чат |
| `GET` | `/widget-demo` | Демо встраиваемого виджета |
| `GET` | `/widget-loader.js` | Скрипт виджета для вставки на сайт |

```bash
curl -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"session_id":"demo","message":"циркуляционный насос, подешевле"}'
```

Ответ:

```jsonc
{
  "session_id": "demo",
  "answer": "…",
  "products": [{"sku": "…", "name": "…", "price": 0, "currency": "RUB",
                "stock_status": "…", "url": "…", "image_url": null}],
  "need_handoff": false,
  "handoff_status": "none",
  "handoff_ticket_id": null,
  "debug": {
    "intent": "broad_category", "category": "pumps",
    "slots": {}, "project_context": {},
    "agents_used": ["IntentRouterAgent", "FeedSearchAgent", "…"],
    "final_answer_source": "deterministic",   // | response_llm | consultant_llm | engineering_interpreter_llm
    "llm_requested": true, "llm_transport_succeeded": true, "llm_output_accepted": false,
    "llm_rejection_reason": "…",
    "topic_changed": false, "products_loaded_from": "file"
  }
}
```

`debug` разделяет три разные вещи: **запрошена** ли LLM, **дошёл** ли запрос
(транспорт) и **принят** ли её вывод после guardrails. Это ключевая
диагностика: `llm_transport_succeeded: true` вместе с
`final_answer_source: deterministic` означает, что модель ответила, но её текст
отклонили.

Перезагрузка фида выключена, пока не задан `RELOAD_FEED_TOKEN`:

```bash
curl -X POST http://127.0.0.1:8000/reload-feed -H "X-Admin-Token: $RELOAD_FEED_TOKEN"
```

Ошибки возвращаются стабильным контрактом `{"error": {"code", "message", "trace_id"}}`;
текст исключения наружу не отдаётся (в нём могут быть URL с credentials).

## Веб-интерфейс и виджет

**Демо-чат** (`/`) — слева переписка и карточки товаров, справа быстрые
запросы, статус фида и debug-блок с интентом, категорией и слотами. Каждая
загрузка страницы начинает новую сессию (`crypto.randomUUID()`).

**Виджет** (`app/static/widget-loader.js`) — самостоятельный embeddable-скрипт
на Shadow DOM: сам создаёт кнопку в углу страницы, изолирует стили от сайта и
ходит в тот же `/chat`.

```html
<script
  src="https://bot.vestatrade.ru/widget-loader.js"
  data-api-base="https://bot.vestatrade.ru"
  data-title="AI-консультант"
  data-position="right"
  data-accent="#0655d9"
  data-quick="Подберите циркуляционный насос подешевле|Подберите электрический котёл для дома 100 м²"
></script>
```

Параметры: `data-api-base`, `data-assets-base`, `data-title`, `data-subtitle`,
`data-greeting`, `data-placeholder`, `data-position` (`right`/`left`),
`data-accent`, `data-width`, `data-height`, `data-z-index`, `data-open`,
`data-show-quick`, `data-quick` (через `|`), `data-persist-session`.

На закрытом интеграционном QA-стенде этот же виджет поддерживает изолированные
режимы `legacy`, `shadow`, `v2_preview` и `auto` через `data-dialogue-mode`.
Режим передаётся в тот же `/chat`; сервер принимает его только при включённом
`DIALOGUE_V2_QA_CONTROLS_ENABLED` и совпадающем `data-qa-token` /
`DIALOGUE_V2_QA_CONTROL_TOKEN`. В публичной установке оба QA-атрибута должны
отсутствовать, а серверный переключатель — оставаться выключенным. Для
параллельного сравнения каждому режиму задают отдельный `data-instance-id`,
чтобы состояния и `session_id` не смешивались.

> `data-persist-session` по умолчанию `true` — `session_id` сохраняется в
> `localStorage` и живёт между визитами. Если нужно, чтобы каждый визит
> начинался с чистого контекста, ставьте `data-persist-session="false"`.

**Демо-витрина** (`/widget-demo`) — имитация магазина, на которой виджет
проверяется в «боевой» обстановке: сайдбар с разделами, поиск, сортировка и
карточки товаров. Витрина собирается из того же фида, что и каталог бота:

```bash
python3 scripts/build_widget_demo_catalog.py          # пересобрать витрину
python3 scripts/build_widget_demo_catalog.py --check  # проверить, не устарела ли
```

Скрипт читает `data/feed_showcase_100_2026-06-14.xml` тем же `FeedLoader`, что и
сервер, раскладывает позиции по разделам тем же `FeedSearchAgent.canonical_category`,
что и поиск, и пишет `app/static/widget-demo-catalog.json` — все 100 позиций и
счётчики разделов. Страница рисует карточки из этого файла, поэтому спросить у
консультанта можно про любой товар, который виден на витрине. Рубрики фида для
разделов не годятся: котлы и насосы лежат в нём в «ПРОКАЧИВАЕМ СКИДКИ».

Для продакшена ограничьте источники: `ALLOWED_ORIGINS=https://vestatrade.ru,https://www.vestatrade.ru`.

## Конфигурация

Все переменные читаются из `.env` в корне `vestatrade_bot/`. Относительные пути
разрешаются от корня проекта.

### LLM

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | `ollama`, `openrouter` или любое другое значение = LLM выключена. `openrouter` без ключа автоматически переключается на Ollama |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Адрес Ollama |
| `OLLAMA_MODEL` / `OLLAMA_MODEL_STRONG` | `qwen3-vl:8b-instruct` | Быстрая / сильная модель |
| `OLLAMA_EMBEDDING_MODEL` | `bge-m3` | Локальная модель поиска по паспортам |
| `OPENROUTER_API_KEY` | — | Ключ OpenRouter |
| `OPENROUTER_MODEL` / `OPENROUTER_MODEL_STRONG` | `qwen/qwen3-vl-8b-instruct` | Модели OpenRouter |
| `LLM_TIMEOUT_SECONDS` | `60` | Таймаут одного вызова вне бюджета реплики |
| `LLM_REQUEST_TIMEOUT_SECONDS` | `180` | **Общий** бюджет на все LLM-агенты одной реплики |
| `LLM_MAX_RETRIES` | `2` | Повторы (повтор не начинает новый бюджет) |
| `LLM_RETRY_DELAY_SECONDS` | `1` | Базовая пауза между повторами |
| `DAILY_BUDGET_USD` | `10` | Дневной лимит расходов |
| `LLM_INPUT_PRICE_PER_1M_TOKENS_USD` | `0` | Цена входных токенов (для Ollama — 0) |
| `LLM_OUTPUT_PRICE_PER_1M_TOKENS_USD` | `0` | Цена выходных токенов |

Если `LLM_PROVIDER=openrouter`, но `OPENROUTER_API_KEY` отсутствует, пуст или
содержит только пробелы, приложение при запуске выбирает Ollama. Все runtime-
агенты, включая semantic interpreter, audit, консультанта и генератор ответа,
используют `OLLAMA_MODEL` / `OLLAMA_MODEL_STRONG`; OpenRouter-модели в таком
режиме не передаются локальному серверу. Это относится к самому боту. Отдельные
платные live-eval/judge-скрипты остаются намеренно OpenRouter-only и без ключа
пропускаются либо завершаются до запуска оценки.

`OPENROUTER_*` варианты старых имён (`OPENROUTER_TIMEOUT_SECONDS`,
`OPENROUTER_MAX_RETRIES`, `OPENROUTER_*_PRICE_*`) поддерживаются для обратной
совместимости.

Сильная модель (`*_MODEL_STRONG`) используется `ConsultantAgent`; по умолчанию
равна быстрой, чтобы без настройки ничего не ломалось.

> **Какой провайдер реально работает.** `.env.example` использует локальный
> Ollama по адресу `http://localhost:11434`. Если этот сервер
> недоступен, `scripts/check_llm.py` покажет `FAILED`, и бот пойдёт полностью
> детерминированным путём — молча, без ошибок. Живые прогоны с LLM выполняются
> через `openrouter` (последний прогон эвалуатора — `qwen/qwen3-vl-8b-instruct`).
> Проверяйте `check_llm.py` перед любым live-прогоном: иначе легко принять
> детерминированный fallback за результат работы модели. То же видно в
> `/health` (`llm_provider`, `llm_configured`) и в `debug.final_answer_source`
> каждого ответа.

### Запуск V2 с Ollama на другом компьютере

После получения актуальной ветки и установки Python-зависимостей достаточно
запустить:

```bash
./scripts/start_v2_ollama.sh
```

Первый запуск сам проверяет или скачивает строго `qwen3-vl:8b-instruct` и
`bge-m3`, выполняет настоящий запрос к Ollama и собирает **тот же**
`app/data/passport_index.json` для локального `bge-m3`. Если индекс был создан
с OpenRouter `baai/bge-m3`, он намеренно пересобирается: смешивать векторы
разных runtime-моделей нельзя. Второй скрипт запускает обычный `/chat` и
витрину в режиме `V2 → Legacy fallback`; `DIALOGUE_V2_FORCE_LEGACY=true`
остаётся мгновенным откатом для процесса.

`./scripts/prepare_ollama_v2.sh`. После успешной подготовки можно не повторять

на этот один запуск и не меняет постоянные настройки Windows.

## Оценка качества (live-прогоны)

`run_bot_evaluation.py` — основной инструмент проверки. Он **не открывает
карточки товаров на сайте**: XML разбирается локально и служит ground truth, а
каждый ответ бота получается через реальный HTTP `/chat`.

```bash
# Локальный сервер должен быть запущен
BOT_API_BASE_URL=http://127.0.0.1:8000 \
  .venv/bin/python run_bot_evaluation.py --suite smoke --output-dir reports/my_run
```

Наборы `--suite`: `smoke`, `core`, `all` (smoke+core), `extended`
(сценарии, сгенерированные из реального каталога), `full`.

Полезные флаги: `--dry-run-catalog` (показать матрицу сценариев без HTTP),
`--rescore <test_results.json>` (пересчитать оценки без новых вызовов),
`--skip-api-probes`, `--extended-limit N`.

Артефакты в `--output-dir`: `test_report.md` (сводка для человека),
`test_results.json`, `test_transcripts.jsonl`. Все артефакты проходят
рекурсивную редактуру credentials перед записью.

Что оценивается: pass rate по диалогам и ответам, доля галлюцинаций, потери
контекста, релевантность уточнений, латентность p50/p95/max, повторяемость на
эквивалентных сценариях, классы ошибок (`MISSED_CONSTRAINT`,
`UNVERIFIED_DYNAMIC_DATA` и т. д.) и приоритетные исправления.

## Эксплуатация

**Один worker** — состояние в памяти процесса, этого достаточно для разработки.
**Несколько workers или контейнеров** — обязателен Redis, иначе клиент будет
попадать в разные процессы и терять контекст:

```bash
SESSION_STORE_URL=redis://:password@redis:6379/0
SESSION_TTL_SECONDS=86400
SESSION_LOCK_TIMEOUT_SECONDS=30
```

**Отказоустойчивость.** Недоступность LLM, исчерпание бюджета или таймаут не
ломают диалог — бот переходит на детерминированный путь. Недоступность фида не
ломает каталог — используется кэш. Пустой парсинг не затирает рабочий кэш.
У Ollama-эндпоинта есть circuit breaker (20 с), чтобы недоступный локальный
сервер не съедал бюджет каждой реплики.

**Приватность.** Контакты и согласие обрабатываются детерминированно **до**
роутера, поэтому PII не уходит во внешнюю модель и не попадает в её кэш-ключ.
Логи переписок редактируют телефоны и почту. Идентификаторы сессий в Redis
хешируются. Тексты исключений наружу не отдаются.

**Продакшен.** Бот развёрнут на `bot-api-vestatrade.ru`. Локальные правки не
попадают туда автоматически — деплой отдельный шаг.
