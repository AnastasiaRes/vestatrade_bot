# VestaTrade: реализация исправлений после OpenRouter-проверки

Дата: `2026-08-21`

## Результат

Исправления реализованы внутри существующего application flow. Повторный
прогон пользовательских диалогов и вызовы OpenRouter на этом этапе не
выполнялись — по запросу заказчика проверка ограничена локальными
детерминированными regression-тестами.

Полная смена архитектуры не потребовалась. Критические ограничения вынесены в
общий слой каталожных фактов, а контекстные факты представлены типизированным
состоянием сессии. LLM больше не принимает решения там, где ответ должен
однозначно следовать из каталога или состояния диалога.

## Реализованные исправления

| Проблема | Исправление |
|---|---|
| Запрос одного размера принимал редукционный/многопортовый SKU | Добавлен общий fail-closed анализ топологии дюймовых присоединений. Запрос `3/4` допускает только товар, у которого подтверждён единственный размер `3/4`; `1/2×3/4` и `1/2×3/4×1/2` исключаются. |
| Router, retrieval и ranking по-разному понимали резьбу | Добавлен общий parser каталожных фактов ВР-ВР / ВР-НР / НР-НР. Exact SKU, обычный поиск, альтернативы и guardrails используют единый контракт. |
| Явные ограничения могли обходиться в shortcut-ветках | `thread_type`, `thread_gender`, `fitting_system`, `angle_deg`, `handle_type`, `full_bore`, `body_form`, `product_kind` проверяются fail-closed; exact SKU также проходит полную проверку slots. |
| `PPR 20×1/2 НР 45°` мог вернуть соседний 90° или другую систему | Система фитинга, угол и резьбовой конец стали hard constraints. При отсутствии точного 45° результат пустой, а не «почти подходящий» SKU. |
| Подтверждение no-match теряло контекст и могло сменить категорию | В сессии сохраняется типизированный `LastSearchOutcome`; непосредственное подтверждение обрабатывается до повторного routing и отвечает по факту предыдущего поиска. |
| «Вернёмся к первому показанному» теряло referent | Фокус товара отделён от последних карточек; сохраняются первый показанный SKU, источник аналогов и отношение source → alternatives. |
| «Какой дешевле? Назовите один» мог выбрать первый, а не минимальный по цене | Для сравнения уже показанного набора детерминированно выбирается одна карточка с минимальной ценой. |
| Опечатка в явно указанном артикуле давала тупиковый no-match | Для запросов с маркером `артикул`/`SKU` добавлена безопасная подсказка уникального близкого SKU. Она не выбирает товар автоматически и просит подтверждение. |
| `артикул 15100Z` не распознавался как SKU | Добавлен отдельный строгий extractor для явно маркированного артикула без ослабления общего эвристического SKU-поиска. |
| Склонения слова «вода» приводили к повторному вопросу о назначении | Общая морфологическая проверка распознаёт `вода`, `воды`, `воде`, `воду`, `водой`, `водою`, а также ГВС/ХВС и водоснабжение. |
| LLM могла неверно расшифровать FM как «фланцевую» | Подтверждение критического типа резьбы формируется детерминированно из typed state: FM = ВР-НР, одна внутренняя и одна наружная резьба. |

## Архитектурное решение

Сохранена текущая архитектура приложения. Добавлены два небольших общих
доменных компонента:

- `product_constraints.py` — единый источник truth для размеров и резьбы;
- `sku_suggestions.py` — ограниченная коррекция только явно введённых SKU.

Диалоговый state расширен `LastSearchOutcome`, `ProductFocusState` и
`ProductRelationContext`. Это устраняет зависимость контекста от визуального
списка последних карточек и позволяет хранить отрицательный результат поиска
как проверяемый факт.

## Следующий gate

Когда будет принято решение повторить проверку, нужен отдельный post-fix live
прогон через локальный HTTP API и реальный OpenRouter: сначала targeted retest
исправленных классов ошибок, затем smoke/core regression с тремя повторами
критических adaptive-сценариев. Текущий результат подтверждает корректность
детерминированной логики, но не заменяет проверку полного LLM-пути.
