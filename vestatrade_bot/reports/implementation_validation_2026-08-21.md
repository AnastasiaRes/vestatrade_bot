# VestaTrade assistant: implementation validation

Дата: `2026-08-21`

## Решение по архитектуре

Полная смена архитектуры, микросервисы, vector DB или замена LLM не требуются.
Основная причина серьёзных ошибок находилась до финальной генерации: одинаковые
ограничения пользователя по-разному трактовались router, retrieval, ranking и
guardrails. Исправление выполнено внутри существующего application flow:

```text
raw user text
  -> typed slots
  -> fail-closed constraint matching
  -> ranking только допустимых SKU
  -> повторная проверка карточек
  -> grounded answer
```

## Что реализовано

- Общий parser резьбовых окончаний различает ВР-ВР, ВР-НР, НР-НР, один
  резьбовой конец комбинированного PPR-фитинга и PPR socket/spigot `вн/нар`.
- Явные `thread_type`, `thread_gender`, `fitting_system`, `angle_deg`,
  `handle_type`, `full_bore`, `body_form` и `product_kind` стали hard
  constraints. Неизвестный факт не считается совпадением.
- Exact-SKU и name-search shortcuts больше не обходят эти ограничения.
- Исправлены сквозные raw-text сценарии: `PPR угол 20×1/2 НР 45°`,
  `шаровой полнопроходной 3/4 ВР-НР`, `валтек 3/4 бабочка`,
  `кран пол дюйма мама мама`, `термогаловка`.
- Ограничения угольника не теряются между router и retrieval; угол `45°`
  сохраняется в `angle_deg` и даёт no-match, если точной позиции нет.
- Аналоги получают подтверждённые facets исходного SKU. Ослаблять можно только
  явно перечисленные поля; различие сообщается пользователю.
- Product focus отделён от списка последних карточек. Сохраняются исходный SKU
  аналога, первый показанный товар и referent для последующих вопросов.
- Turn стал транзакционным: при исключении состояние диалога откатывается.
- Сравнение `исходный и первый аналог` выбирает ровно две позиции;
  эквивалентные записи резьбы не выдаются за различие.
- Добавлено опциональное общее Redis-хранилище с TTL, хешированными ключами и
  per-session distributed lock. Без URL сохраняется прежний in-memory режим.
- Добавлены `/ready`, ограничение размера API-входа, стабильный redacted 500
  contract и fail-closed защита `/reload-feed`.
- Административная перезагрузка удалена из публичной web-панели и оставлена
  только в token-protected API.
- Evaluator теперь проверяет релевантность уточнения, каждое ослабление аналога,
  явную привязку `самого дешёвого` к SKU и исправленный, а не отвергнутый размер.

## Проверка

- Полный pytest suite: **996 passed**, 1 стороннее deprecation warning
  (`Starlette TestClient` / `httpx2`), 0 failed.
- Python compile check: PASS.
- `git diff --check`: PASS.
- Локальный каталог: **14 035** загруженных товаров, source=`file`.
- HTTP: `/health` = 200, `/ready` = 200, невалидный payload = 422.
- HTTP `PPR 20×1/2 НР 45°`: `angle_deg=45`, карточек нет.
- HTTP `шаровой полнопроходной 3/4 ВР-НР с бабочкой`: после релевантного
  уточнения назначения показаны только совпадающие по hard constraints SKU.
- HTTP `мама мама`: сохранён `thread_type=ff`; ВР-НР не попадает в выдачу.
- HTTP exact SKU -> analogs -> compare: исходный `VT.217.N.04` сохранён;
  сравнение с первым аналогом содержит только `VT.217.N.04` и `VT.217S.N.04`.

Во время проверки запросы к `vestatrade.ru` и `www.vestatrade.ru` не
выполнялись. URL из XML/API рассматривались только как строки.

## Контроль качества evaluator

Старые 50 диалогов / 137 user turns были пересчитаны без новых HTTP/LLM
вызовов. Более строгая оценка старых ответов: **64,96% PASS по turns**,
48 FAIL вместо прежней завышенной оценки. Это baseline старых transcript'ов,
а не post-fix результат.

## Незакрытые release gates

1. После исправлений не выполнен новый live OpenRouter smoke/core прогон.
   Настроенный Ollama был недоступен; передача запросов и каталожного контекста
   внешнему OpenRouter была заблокирована средой до отдельного явного
   разрешения. Credentials нигде не выводились.
2. Redis contract покрыт unit-тестами с совместимым client double, но перед
   multi-worker production нужен integration test с реальным Redis и
   искусственным restart одного worker.
3. Нужен новый live suite: 10 smoke, затем не менее 40 adaptive dialogues и
   три повтора similar-SKU/analog/correction/context сценариев.
4. Перед публичным deployment рекомендуется отключать подробный `debug` в
   `/chat` либо защищать его отдельной конфигурацией.
5. Осталось обновить зависимость тестового клиента после миграции Starlette на
   `httpx2`; это не влияет на runtime API.

## Статус

**READY WITH ISSUES** для staging и post-fix live evaluation.

Production readiness пока не подтверждён: обязательный следующий gate — новый
прогон с реальной LLM через тот же локальный HTTP API.
